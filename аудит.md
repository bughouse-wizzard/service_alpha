Zakupki-Analyzer: Analysis of Search Issues and Fix Plan
1. Root Cause of HTTP 422 on Search Creation (POST /api/search/)
Dependency Injection (DI) Misconfiguration: The primary cause of the 422 Unprocessable Entity error when creating a search is an incorrect FastAPI dependency setup for the SearchService. In the current implementation, the SearchService.__init__ requires a database session (db) and an event broker (broker) as constructor arguments, but they are not provided via Depends. Because of this, FastAPI attempts to inject db as a query parameter (which it cannot find)[1]. Additionally, broker (of type RedisEventBroker) is not bound to a dependency at all, so FastAPI doesn’t know how to create it[2]. This misconfiguration leads to validation failure on the request: FastAPI essentially expects db in the query string, resulting in a 422 error before the request body is even processed[1].
Payload Schema Mismatch: Even aside from DI issues, the JSON payload sent from the frontend does not conform to the Pydantic model SearchCreateRequest, causing validation errors. The frontend’s startSearch function builds a payload with keys like ktru_code, manufacturer_target, customer_region, limit_contracts, execution_statuses, and specs_text[3]. The backend model expects different field names (with aliases in some cases). For example, the model expects ktru (alias allows ktru_code), manufacturer (instead of manufacturer_target), region (instead of customer_region), and contract_limit (instead of limit_contracts)[4]. Crucially, the frontend uses "specs_text", but the model expects characteristics (alias for an internal target_specs_text field) – since no alias or field matches "specs_text", this field is unrecognized[5]. Likewise, the frontend fixes customer_region to "SZFO" (North-West Federal District in Latin characters), whereas the backend’s default example was “СЗФО” (in Cyrillic)[6]. The execution status codes are sent as ["EC", "ET"] (likely abbreviations for "Execution Completed/Terminated"), but the model may expect full status strings (e.g. “Исполнение завершено/прекращено”) or at least needs to translate those codes[7]. Although the Pydantic model is configured with populate_by_name=True to allow aliases, some fields like specs_text have no corresponding alias in the model, leading to a validation error. Moreover, date fields are sent as "YYYY-MM-DD" strings without time – Pydantic can parse dates, but the format isn’t explicitly documented and could potentially cause parsing issues[8]. All these discrepancies combined cause the request body to fail validation, resulting in a 422 error response from the POST endpoint[8].
Fields Sent vs. Model Definition: In summary, the frontend is sending a JSON that the backend isn’t expecting. Key differences include: using ktru_code instead of ktru (this one is actually handled via alias), using manufacturer_target instead of manufacturer, customer_region instead of region, limit_contracts instead of contract_limit, and specs_text instead of characteristics. The SearchCreateRequest model and its aliases need to match the frontend, or vice versa. Currently they do not, leading to Pydantic ValidationError for unknown/incorrect fields[4]. Thus, even if the DI issue were fixed, the payload as-is would not pass validation without aligning these field names.
2. Frontend Display Issues: Search History and Results
2.1 Search History Not Loading on Page Open
When the main page loads, the application is supposed to fetch the list of past searches via GET /api/search?page=1&page_size=50 and display the history. However, the history list is not appearing as expected. The likely reason is a mismatch in the expected response format versus the actual API response. The frontend code expects the response JSON to contain an items array of search records, which it then maps to the SEARCH_HISTORY list[9][10]. If the backend returns the list of searches in a different field (for example, a field named results or as a bare list without an enclosing key), the frontend’s code would not find data.items and would throw an error, resulting in the catch block being executed. Indeed, the backend defines a SearchListResponse model (list of SearchBrief plus pagination info), which in code appears to use a field results for the list[11]. The UI, however, looks for data.items[12]. This discrepancy would cause loadSearchHistory() to fail (triggering the "Не удалось загрузить историю поисков" error toast) and leave SEARCH_HISTORY empty[13].
Additionally, there was a minor issue with status mapping. If any search had status "DONE" or "ERROR" in the database (as set by the backend upon completion/failure), the frontend’s mapStatus would not recognize these and return them as-is[14]. In such a case, the history entry would show raw "DONE" or "ERROR" text instead of the expected “Завершен” or “Ошибка”. This is confusing to users and indicates a status enum mismatch between front and back. However, this is a display issue; it wouldn’t prevent the list from loading, it would just show the wrong status text[14]. The primary cause of not loading at all is the JSON structure mismatch described above. In short, the history fetch doesn’t populate because the frontend is not interpreting the response correctly. Aligning the backend’s output to include an items list (or adjusting the frontend to use the correct field) will fix the history display. Notably, the search history is fetched from the real backend (not mocked), so this integration needs to be correct. The audit found that backend’s SearchBrief model does include fields for contracts_found and nmc_value (which likely serialize as found_total and nmc_value in JSON), matching what the UI expects to display[15]. That is fortunate – otherwise, the UI would show 0 or “–” for those values. Ensuring the response structure matches (e.g., returning { items: [...] }) will allow the history to load properly with the correct data.
2.2 “Undefined” Fields in Search Results Table
After a search is run and the user opens the Results tab, the table of contract results is supposed to show details of each found contract (ID, date, price, manufacturer, match type, etc.). Currently, these fields are appearing as blank or “undefined” in the UI. This is directly caused by a disconnect between the backend’s /api/search/{id}/results response and what the frontend code expects. The frontend’s loadResultsFromAPI function assumes the response JSON will have an items list of results, where each item includes keys like contract_id, published_at, price, is_identical, manufacturer, ai_score, is_2025_plus and so on[16][17]. However, the current backend returns a different schema. According to the analysis, the backend returns each result with fields like id, reestr_number, contract_url, sign_date (which is the contract date), unit_price, currency, match_type, ai_score, manufacturer_found, etc.[18]. Notably missing in the response are the fields that the UI tries to use: - contract_id: The UI expects a unique contract identifier field. The backend is likely using id (UUID of the ContractResult in the database) and does not alias it to contract_id. So item.contract_id is undefined on the frontend[19]. - published_at: The UI expects the contract signing date under this key, but the backend uses sign_date without aliasing it to published_at[20]. Thus, item.published_at is undefined for each result. - price: The UI expects a total contract price field. The backend currently only returns unit_price and possibly misses a field for the total contract price. If the total price is not included (or is embedded in a raw JSON), item.price will be undefined[21]. Indeed, the analysis noted that contract_price was not returned at all in the current API[21]. - manufacturer: The UI expects the found manufacturer name under item.manufacturer. The backend uses manufacturer_found as a field, which the UI isn’t reading (and there was no mapping to manufacturer)[18][22]. - is_identical: The UI expects a boolean or flag indicating if the contract’s specs exactly match (identical) or just similar (homogeneous). The backend returns match_type (e.g., "IDENTICAL", "HOMOGENEOUS", or "UNKNOWN")[18]. The UI’s current code tries to derive a text label from item.is_identical (a boolean)[23]. Since is_identical isn’t provided (and not derived on the UI because match_type wasn’t mapped), this logic breaks. Essentially, item.is_identical is undefined, so the UI might treat it as falsy (thus labeling everything as "Однородный" by default), which is incorrect.
Because of these mismatches, when loadResultsFromAPI tries to map the response to currentContracts, it ends up creating objects with properties like id: undefined, date: undefined, price: undefined, manufacturer: undefined[19]. This obviously prevents the results table from displaying meaningful data. All contract IDs show as blank/undefined (making selection checkboxes malfunction since they rely on IDs), dates and prices don’t show up (or may show as invalid values like NaN for average price calculations), etc.[24]. In practice, during testing, the developers likely relied on a fallback to mock data which masked this problem. Indeed, the frontend code catches any error in loading results and calls loadMockResults() to generate fake results[25][26]. The report indicates that currently the UI always ends up using the mock results because the API format “doesn’t match” what the UI expects, causing the fetch to be treated as failure and triggering the fallback[27]. This means users see a filled table of dummy contracts, which hides the fact that real data wasn’t used[28]. To fix this, the backend and frontend need to agree on a common format: - The backend should include all necessary fields in the JSON (contract unique ID, contract date, total price, customer name, etc.), either by renaming/aliasing existing fields or adding any missing ones[20][19]. - The frontend should be adjusted to use the fields provided by the backend after these changes (for example, if match_type is provided instead of is_identical, the UI should map that to the appropriate display text)[29][30].
Once the format is aligned and the UI stops always falling back to mock data, the results table will display real contract data properly (contract numbers, dates, prices, match type, manufacturer, AI score, etc.)[31]. This is a critical integration fix to make the MVP functional with actual data instead of placeholders.
3. FastAPI SearchService Dependency Issues (Database & Broker)
The analysis uncovered several problems with how SearchService and its dependencies are wired in FastAPI:
•	Database Session Injection: The SearchService is supposed to use a database session (AsyncSession) provided by Depends(get_db). However, in the current code, the service’s constructor does not declare db: AsyncSession = Depends(get_db). Instead, some routes were written to accept a db parameter themselves. For instance, the create_search endpoint in app/api/search.py originally had a function signature including db: AsyncSession = Depends(get_db)[32]. This caused FastAPI to treat db as a required dependency from the query, which is incorrect for a request body POST – leading to the 422 error as discussed. The intended design (and partially implemented fix) was to remove db from the router function and let SearchService = Depends() internally handle the DB session injection[32]. However, since SearchService.__init__ didn’t specify that dependency, FastAPI wasn’t injecting it at all, or was confused by it. This mismatch must be resolved by moving the Depends(get_db) into the SearchService itself (as default values for the constructor parameters)[33], and removing db from the route function signatures.
•	Event Broker Dependency: Similarly, SearchService uses an event broker (for Server-Sent Events via Redis streams). The service expects a RedisEventBroker instance, but currently it’s not provided by FastAPI’s dependency system at all[2]. The service might be constructing its own broker internally or simply not functioning properly. In the route, SearchService is requested via Depends() with no parameters, so FastAPI tries to instantiate it. It will attempt to provide arguments by type-hint matching: it might succeed in providing a DB session (because FastAPI sees the AsyncSession type and finds a dependency for it), but it has no provider for RedisEventBroker, likely causing an initialization error[34]. Indeed, the framework may throw an error or instantiate RedisEventBroker with default constructor (which might connect to Redis without proper config). The dev logs indicated FastAPI was “expecting parameter db in query”, which was one symptom[35], but it’s possible that even if that were resolved, the missing broker could cause a crash or malfunction. The fix is to supply the broker via dependency as well. One approach is to define a get_event_broker() function (similar to get_db) that returns a broker instance (possibly a globally initialized one), and declare broker: RedisEventBroker = Depends(get_event_broker) in the SearchService constructor[33]. This way, FastAPI will inject a properly constructed broker. Alternatively, the broker could be created once on startup (e.g., stored in app.state) and the dependency just returns that. The goal is to avoid FastAPI trying to treat broker as a query param or failing to provide it[2].
•	Incorrect Usage of Depends in Class: The SearchService class itself was not decorated or declared as a dependency provider. Normally, one might use Depends(SearchService) if SearchService were a dependency class with its own __call__. In this project, they instantiate it directly via Depends() which relies on FastAPI's ability to call the constructor. This works if the constructor parameters themselves are dependencies. Therefore, after adding Depends(get_db) and Depends(get_event_broker) to SearchService.__init__, using service: SearchService = Depends() in routes will correctly create the service with both a DB session and broker injected[34]. Ensuring all routes (create search, list searches, get results, stop search, etc.) use this pattern is important so that we don’t accidentally reintroduce the 422 via any stray db parameters in function signatures[36].
In summary, the DI issues were a major factor in the API failing. Fixing them involves updating the SearchService constructor to properly accept dependencies for db and broker[33], and cleaning up the router functions to not separately demand a db session[36]. Once done, FastAPI will no longer misinterpret db as a query param, and the service will have the required components. This resolves the backend-side errors that led to HTTP 422 and ensures the search endpoints can be called without low-level injection errors.
4. DeepSeek AI Integration and Operation Without API Key
Zakupki-Analyzer uses an AI service called DeepSeek to normalize text and compare product specifications (for determining if a contract is an identical match or just homogeneous). However, not all deployments will have a DeepSeek API key. It’s crucial that the system still functions (perhaps with degraded capability) when the AI is unavailable.
Current Behavior without Key: The code is written such that if settings.deepseek_api_key is not provided, the DeepSeekClient either raises an exception or returns None for its operations[37]. The pipeline is wrapped to handle this: if no AI result is obtained (compare_res = None), the system continues without crashing[38]. But the consequence is that every contract’s match type defaults to “NO_MATCH”/UNKNOWN, and the AI score is 0[39]. Essentially, without AI, the logic that distinguishes identical vs homogeneous vs unmatched contracts is bypassed – the MVP logic that was supposed to classify matches (e.g., “identical if all key specs match; homogeneous if above X% match”) was not implemented with a heuristic, they fully relied on the AI service[40]. So currently, with AI off, all contracts are treated as if they did not match the specs (which is not very useful to the end user). The UI will show all AI Scores as 0 and likely mark all results as "Однородный" or "Неизвестно" because match_type comes through as UNKNOWN for all[39]. The good news is that the system doesn’t crash – it’s effectively “stubbed” in that it runs, but the feature is non-functional in terms of meaningful output.
Ensuring Isolation: We must ensure that if the DeepSeek API key is absent, the system neither tries to call the external service nor throws unhandled exceptions. The current design does catch the situation, so stability is maintained[38]. For improvement, we can implement a fallback logic or at least better defaults: - One suggestion is to implement a simple heuristic: e.g., if no AI, consider a contract “IDENTICAL” if all the keywords from the search’s object_name or characteristics are found in the contract specs text; consider it “HOMOGENEOUS” if at least one matches, otherwise “UNKNOWN”. This is a rough approximation but could provide some meaningful differentiation[41]. - Alternatively, since the MVP requirement wanted an indication of identical/homogeneous, even a basic string similarity check or count of spec matches could be done when AI is not available. This would prevent the scenario where everything is marked unknown. - If implementing such logic is too complex or out-of-scope, another approach is to hide or downplay the AI-related fields in the UI when AI is off. For example, if ai_score is always 0, the “AI Score” column could be hidden or a note could indicate AI is not enabled[41]. However, the requirement was to include this, so more likely we want to implement at least a minimal functionality.
Integration with Fallback: It’s crucial that whatever we do, it’s isolated behind the same interface. Perhaps modify DeepSeekClient to have a no-key mode that uses a local function for compare. The code should check if not settings.deepseek_api_key: ... and then either skip calling external API or use a dummy comparator. The analysis noted that currently the integration is effectively disabled (no key means no comparisons)[40], so the system doesn’t crash, but it also doesn’t deliver the intended value. We need to ensure this state doesn’t cause any downstream crashes – for instance, the comparison data modal always shows “Нет данных” (no data) which is expected because no comparisons were generated[42]. The absence of DeepSeek also means match_type values are mostly UNKNOWN or HOMOGENEOUS and score=0 for all results[43], which might simplify some logic (like auto-selecting top 3 just defaults to the first 3 by date). The key point: the system should continue to work with mock or default data when AI is off, and not throw errors. Based on the code review, it does continue working (with limitations in output quality)[39].
We should double-check that any calls to DeepSeek (normalize or compare functions) are in try/except blocks or gated by the presence of the API key. From the description, it appears they are – no uncaught exceptions were reported, just the outcome of no AI. Moving forward, implementing the fallback logic for match type or clearly documenting that AI features are disabled without a key would improve the user experience. The system should not rely on DeepSeek for stability, and indeed after these adjustments, it will not crash without it.
5. Summary of Identified Errors and Discrepancies
Through the analysis, we identified several critical issues in the current system that explain why key features are not working. Below is a summary of these findings:
•	Dependency Injection Errors: The FastAPI dependency setup for the search functionality was incorrect. The SearchService was not receiving a DB session or event broker via Depends, leading to FastAPI treating them as missing parameters. This misconfiguration caused the POST /api/search/ endpoint to throw 422 errors before even processing the request body[1][34]. It likely also impacted other endpoints (any route depending on SearchService). Fixing the DI (adding Depends(get_db) and Depends(get_event_broker) in the service constructor, and removing extraneous db parameters from route functions) is required[33][36].
•	Frontend/Backend Model Mismatch (Search Creation): There is a clear discrepancy between the JSON the frontend sends for a new search and what the backend expects. The field names differ (e.g., specs_text vs characteristics, customer_region vs region, etc.), and some values don’t match expected formats (status codes, region abbreviation)[5][4]. This causes the backend’s Pydantic model validation to fail, resulting in errors (422). The models do use aliases and population by name, but not all cases were covered (e.g., no alias for specs_text). The fix here is to synchronize the request schema: either adjust the frontend to send the exact keys the backend expects, or adjust the Pydantic model to accept the keys the frontend sends. Given that both codebases are under our control, the simplest path is to change the frontend payload to match the backend model (e.g., use characteristics, region, contract_limit, etc. in the JS payload)[44]. Aliases can also be added on the backend for flexibility. In short, request fields and model fields must align.
•	Response Model Mismatch (Search Results): The data returned by the backend for search results does not match the frontend’s expected structure. Key fields like contract_id, published_at (contract date), price (total contract price), manufacturer, and a boolean is_identical are missing or named differently[19]. The backend returns some equivalent information (id, sign_date, unit_price, manufacturer_found, match_type), but without the same names or complete data, the frontend cannot bind them to the UI[45]. This led the UI to display undefined values and revert to mock data. To resolve this, the backend’s /api/search/{id}/results should be modified to return a unified result schema that includes all necessary fields in the expected format[29][46]. For example, include contract_id (which can just be the id alias), published_at (use sign_date but formatted or aliased), price (compute or parse the total contract price from stored data), manufacturer (map from manufacturer_found), and perhaps directly provide a match_type or boolean flags as needed. Concurrently, update the frontend code loadResultsFromAPI to use the new fields (or adjust if we keep slightly different names). This contract between front and back must be consistent. After fixing this, the real results will populate correctly, eliminating the need for dummy data.
•	Search History Discrepancies: Although the history list is fetched from the backend, there were minor mismatches. The backend’s SearchBrief model lacked a region field in the schema, yet some tests expected it[47]. The status values as stored could be “DONE”/“ERROR” which the frontend didn’t map to user-friendly strings[14]. Also, if the backend’s list response used results vs items, that needed alignment. These inconsistencies meant that on page load, the history might not render or might show improper values. By fixing the API output (using the same key names as the front expects) and ensuring status enums are consistent (e.g., use “completed” instead of “DONE”)[14], the history table will load and display correctly. Fortunately, fields like found_total (contracts found) and nmc_value (calculated average price) were coming through and being handled, as SearchBrief included them (often under aliases)[15]. We need to double-check that the list endpoint’s JSON structure matches what the front-end code expects, to avoid runtime errors in loadSearchHistory().
•	Selection (Top-3 Contracts) Issues: The process for selecting the top 3 contracts (either automatically or manually via checkboxes) has a few bugs. The backend expects a PATCH to /api/search/{id}/selection with a list of registry numbers (selected_reestr_numbers) per the current schema[48]. The frontend, however, sends selected_contract_ids (a list of internal UUIDs of contracts)[48]. This mismatch means the backend either ignores the field or throws a validation error (422) because it doesn’t recognize selected_contract_ids. Consequently, when users try to select or deselect contracts in the UI, the request fails – the UI shows a toast “Ошибка обновления выбора” (error updating selection)[49]. Additionally, the router’s response_model for this endpoint was declared as List[SearchResultItem], but the service method was returning a full SearchDetailsResponse or simply nothing/bool[50]. This is an inconsistency in API design (not currently breaking the UI because the UI doesn’t consume the response, but it’s a bug). The fixes would be: unify the selection request format (preferably have the backend accept selected_contract_ids as the frontend uses, since using the internal IDs is fine for our case)[51][52], or change the frontend to send registry numbers (less ideal). Then, adjust the backend to return either an updated list of results or a confirmation model (and correct the response_model accordingly)[50]. After this, selecting top-3 contracts will work seamlessly: no error toasts, and the selection state will be saved in the backend (allowing consistent behavior like including the accepted_for_nmc flags in results).
•	Missing API Endpoint (Comparison Data): The frontend tries to GET /api/search/results/{result_id}/comparison when the user opens the “Сравнение характеристик” modal. However, no such endpoint exists in the current backend. There is a service method get_comparison_data but it’s not wired to any router, so the call returns 404 and the UI always shows “Не удалось загрузить данные сравнения” (failed to load comparison data) in the modal. This is clearly a functionality gap. The fix is to implement this endpoint and return the structured comparison data. Additionally, the current get_comparison_data implementation is incomplete: it attempts to read from result.raw_data_json["comparison"] which is always empty, because the comparison rows are actually stored in a separate database table (spec_comparison_row) and not inserted into that JSON[42]. So, we need to change get_comparison_data to actually query those comparison rows (either via an ORM relationship or a direct query) and return them in the response[53][54]. Once the endpoint returns data, the UI modal will be able to display actual differences (or a message if none). This will move the feature from “always showing no data” to working as intended (assuming the spec comparisons are generated when AI is active; if AI is off, the rows might still be empty, but at least the endpoint will exist).
•	Status Enum Mismatch: As noted, the backend uses internal status codes like "PENDING", "RUNNING", and then sets "DONE" or "ERROR" when finished[55]. The Pydantic schema SearchStatus enum uses "pending", "running", "completed", "failed", etc., and the frontend relies on those strings for mapping to display text[55]. The fact that "DONE" and "ERROR" appear (not in the enum) means the final status stored in the database/search object is inconsistent. This can confuse the UI (it displayed "DONE" raw)[14]. We should standardize on one set of status values. The simplest solution is to modify the worker pipeline to set status to "completed" instead of "DONE", and "failed" instead of "ERROR"[56]. That way, the SearchStatus enum and the values in the DB align with what the frontend expects. Correspondingly, the SSE “done” event should carry status: "completed" or "failed" as well[57]. The UI mapping will then correctly show “Завершен” or “Ошибка” via mapStatus[14]. Consistency here will prevent any odd unmapped labels and is closer to the spec/requirements.
•	SSE Event Content: The Server-Sent Events are used to update progress and notify when the search is done (or if new results come in). It was found that the "done" event currently may not include all the information the frontend expects. For instance, when a search finishes, the UI expects the SSE "done" event’s data to contain found_total (number of results found) and nmc_value (calculated average price) in order to update the history entry immediately[58]. In the current backend, the "progress" events do send found_total, but the final "done" event did not include these fields, leading to the UI not updating the “avg” field until a manual refresh or until results are fetched[59]. We should enhance the SSE done payload to include found_total and nmc_value[59]. The backend knows these values at completion (it has search.found_total and search.nmc_value ready), so it’s a matter of packaging them in the event. Similarly, for an "error" event or if stopped, including an error_message or proper status would help. These changes will ensure the UI can immediately reflect the final count and average price when a search completes (the UI code is already prepared to use those if present)[60].
•	Miscellaneous Issues: There were some minor code quality and consistency issues noted:
•	Duplicate/unused code: e.g., older methods create_and_start and request_stop in SearchService that aren’t used by the API (superseded by create_search and stop_search)[61]. These can confuse developers and should be removed or updated to avoid divergence.
•	Test expectations out of sync: e.g., tests expecting ValueError on certain validation but Pydantic now raises ValidationError, tests expecting fields that no longer exist in models (like region in SearchBrief)[47][62]. The automated tests need updating to match the fixed models and behaviors.
•	Use of blocking calls in async code: for example, time.sleep() was used in an async context (the retry loop for HTML fetching) which should be await asyncio.sleep()[63]. These are potential performance issues and should be corrected to not block the event loop.
•	Logging and error messages: by and large logging is good, but we should ensure any exceptions (like invalid input cases) are turned into clear API errors. For instance, if date_to < date_from is supplied, the system currently just ends up with 0 results; adding a validation in SearchCreateRequest to catch that and return a 400 with a message would improve UX[64].
•	Documentation and comments should be updated after fixes: The README and API docs (Swagger) should reflect the final state of the API, including correct example requests and responses, so that frontenders and testers know the expected formats[65].
These issues collectively explain why the system, in its current form, fails to perform the key functions. The search was not starting due to 422 errors, the results were not displaying due to data mismatch, and certain features like comparison and report download were stubbed or broken. The next step is to address each of these issues in a coordinated manner.
6. Test Coverage Evaluation
The project does include a test suite (both unit tests for schemas/services and some integration-like tests), but the coverage and currency of those tests need review:
•	Existing Tests: There are tests for the Pydantic models and some API endpoints. For example, test_schemas constructs a SearchCreateRequest and ensures fields are set, creates SearchBrief and SearchDetailsResponse objects, etc.[66][67]. This indicates the models have been tested in isolation. There are also references to tests for events (EventBroker) and repository instances[68]. However, given the issues found, some tests were likely failing or were not updated to reflect code changes. The analysis pointed out that tests expected fields that were removed or changed:
•	A test expected SearchBrief to have a region field (perhaps to match the spec), but the actual model didn’t have it, causing a test failure[47].
•	A test expected that providing contract_limit=0 to the schema would raise a ValueError (probably according to spec), but Pydantic’s validation raises a ValidationError (which wasn’t caught as ValueError)[62]. This is a mismatch between test expectation and actual behavior – the test likely hasn’t been updated since switching to Pydantic’s built-in validation.
•	Tests constructing SearchDetailsResponse might have expected started_at/completed_at timestamps, which were not actually implemented (the model uses date_from/date_to for filtering instead)[69][47]. Such tests would fail or be irrelevant now.
•	Areas Lacking Tests: Certain functionalities were not covered by tests:
•	SSE events and live search flow: It’s mentioned that SSE and worker processes are hard to test in unit tests, and indeed there are no explicit tests for the streaming events or Celery tasks[62]. After refactoring, it would be beneficial to have at least a simulated test of a search lifecycle (perhaps by mocking the search pipeline or calling the search functions with dummy data) to ensure that statuses and results propagate as expected.
•	Frontend integration: There are no automated tests for the frontend (likely a manual test approach). Once the API is fixed, writing some integration tests (for example, using Playwright or Selenium to simulate a user search) could be valuable, but at minimum the backend tests should simulate the scenarios that the frontend would encounter.
•	Edge cases: Tests should be added for things like the selection endpoint (making sure selecting with wrong IDs yields an error, correct IDs updates the model)[70][51], the report download endpoint (once implemented, test that it returns a file/stream), and the comparison endpoint (after implementation, test with a mock result that has comparison rows).
•	Validation logic: If we add validators (e.g., to check date ranges or to convert status codes), tests should confirm those work (e.g., ensure that "EC"/"ET" are accepted and translated to Russian statuses, or that an invalid region code yields a clear error).
•	Test Updates Needed: After fixing the models and endpoints, the tests must be updated accordingly:
•	Remove or update expectations for fields that no longer exist (like region in SearchBrief if it’s not included, or add it if we decide to include it).
•	Adjust assertions to expect ValidationError instead of ValueError where appropriate (or modify the code to raise ValueError deliberately if that was in the spec and is considered important)[62].
