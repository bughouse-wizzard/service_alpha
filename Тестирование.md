1) Сквозной бизнес-воркфлоу системы (как “должно работать”)
1.1. Этапы одного поиска (state machine)

Статусы поиска:
CREATED → RUNNING → (DONE | STOPPED | ERROR)

Внутренние шаги воркера (каждый шаг логируется):

ValidateInput (проверка параметров)

FetchSearchResults (получение found_total + списка контрактов)

IterateContracts (до лимита)

Для каждого контракта:

FetchContractCard

ParseCommonInfo

ParsePaymentsAndObjects (спецификация)

FetchAttachments

(если 2025+) DownloadPrintForm

ExtractText (pdf/docx)

NormalizeSpecs

LLMCompareAndScore

PersistResult

EmitProgressEvent

FinalizeSearch (подсчёты, автоселект топ-3, НМЦК)

1.2. UI события (что должен видеть пользователь)

После “Начать поиск”:

новый элемент в “История поисков” со статусом “В работе”

прогресс и поступающие результаты “вживую”

В “Результаты поиска”:

таблица заполняется по мере обработки

топ-3 закрепляются сверху (по умолчанию)

модалка сравнения работает

НМЦК пересчитывается при изменении выбранных

2) Сквозные тесты через браузер (E2E) — детальный чек-лист

Ниже сценарии в формате: Цель → Шаги → Ожидаемый результат → Что смотреть в логах.
Это “регрессионный набор” для каждого релиза.

E2E-01: “Счастливый путь” — ручной поиск по КТРУ

Цель: доказать, что полный пайплайн от параметров до НМЦК работает.

Шаги в браузере

Открыть главную страницу.

В “Новый поиск” заполнить:

КТРУ (валидный),

Регион (СЗФО),

Период “3 года”,

Статусы “исполнение завершено/прекращено”,

Лимит 10 (быстро для теста),

Текст характеристик (2–5 штук).

Нажать “Начать поиск”.

Перейти в “История поисков” и открыть созданный поиск.

Перейти в “Результаты поиска” и дождаться статуса DONE.

Проверить:

found_total заполнен,

есть строки результатов,

есть AI score,

есть тип (идентичный/однородный),

выбранные топ-3 закреплены сверху,

НМЦК рассчитан.

Ожидаемо

Статус меняется: RUNNING → DONE

Прогресс увеличивается до processed_count == limit

Результаты не дублируются

НМЦК не пустая и соответствует выбранным 3

Логи (backend/worker)
Ищем по search_id:

ValidateInput OK

FetchSearchResults found_total=...

Для каждого контракта: шаги парсинга и PersistResult OK

FinalizeSearch nmc=... selected=3

E2E-02: “Остановить поиск” (Stop)

Цель: проверить управляемость процесса и консистентность данных.

Шаги

Запустить поиск с лимитом 30.

Через 3–10 секунд нажать “Остановить”.

Убедиться, что статус стал STOPPED.

Результаты должны остаться в таблице, но обработка прекращена (счётчик не растёт).

Ожидаемо

processed_count перестаёт увеличиваться

В UI статус “Остановлен”

Никаких “поздних” результатов после stop (допустимо 1–2 результата “в полёте”, но это фиксируем как правило: graceful stop).

Логи

Stop requested (backend)

Worker received stop flag (worker)

FinalizeSearch status=STOPPED

E2E-03: Фильтры/пагинация “Истории поисков”

Цель: доказать, что таблица истории полностью функциональна.

Шаги

Иметь 10+ поисков (можно наклепать).

Применить фильтр по:

КТРУ

статусу

дате

Проверить пагинацию.

Открыть поиск из любой страницы пагинации.

Ожидаемо

Фильтры работают сервер-сайд (важно)

Пагинация корректна, стабильно возвращает одни и те же данные

Логи

GET /api/search?page=...&filters... с request_id

Время ответа приемлемое (без N+1 запросов в БД)

E2E-04: Фильтры/пагинация “Результатов”

Цель: проверить фильтрацию результатов по AI score и типу совпадения.

Шаги

Открыть поиск с 20–30 результатов.

Поставить фильтр AI score ≥ 80.

Поставить match_type = IDENTICAL.

Проверить пагинацию.

Ожидаемо

Кол-во результатов меняется ожидаемо

На разных страницах нет дублей/пропусков при одном и том же фильтре

Логи

SQL запросы корректны (по индексам)

Нет таймаутов

E2E-05: Модалка “Сравнение характеристик”

Цель: показать, что сравнение прозрачно и объяснимо.

Шаги

В результатах нажать “Сравнение” у любой строки.

Проверить:

target vs actual,

статус MATCH/DIFF/UNKNOWN,

причина (если есть).

Ожидаемо

Данные соответствуют результатам AI score

Нет пустых таблиц “из-за ошибок”

Логи

LLMCompareAndScore OK или обработанная ошибка с fallback

В БД есть spec_comparison_rows для контракта

E2E-06: Ручная смена выбранных 3 контрактов + пересчёт НМЦК

Цель: проверить бизнес-логику НМЦК и устойчивость UI.

Шаги

Снять галочку с одного из top-3.

Поставить галочку на другом контракте.

Проверить:

топ-3 сверху обновились,

НМЦК пересчиталась,

“средняя цена” (если в UI показывается) обновилась.

Ожидаемо

Пересчёт мгновенный/быстрый

Состояние сохраняется (при обновлении страницы — если MVP предусматривает сохранение выбора в БД)

Логи

E2E-07: Загрузка ТЗ файлом (если включено в MVP)

Цель: проверить извлечение требований и автозаполнение.

Шаги

Логи

3) Негативные и “краевые” E2E-сценарии (обязательно)
NEG-01: Некорректный КТРУ

Шаги: ввести мусор → “Начать поиск”
Ожидаемо: 400 с ошибкой валидации + UI-сообщение, поиск не стартует.
Логи: ValidateInput FAILED без падения worker.

NEG-02: Ничего не найдено (found_total = 0)

Ожидаемо: статус DONE, результаты пустые, отчёт пустой, UI “ничего не найдено”.
Логи: FetchSearchResults found_total=0, FinalizeSearch DONE.

NEG-03: Сайт не отвечает / таймаут

Ожидаемо: ретраи, затем статус ERROR (или DONE со “частичной обработкой”, но лучше ERROR с причиной).
Логи: ExternalServiceError timeout, retry=..., итоговый status=ERROR.

NEG-04: Частично “ломаная” карточка контракта

(например, нет вкладки/изменился HTML)
Ожидаемо: контракт помечен как NO_MATCH или PARSE_FAILED, поиск продолжается дальше.
Логи: ParseError, сохранение результата с reason.

NEG-05: LLM вернул невалидный JSON / 500 от провайдера

Ожидаемо:

система не падает,

контракт получает ai_score=null или score=0 и decision=REVIEW,

в UI видно, что AI не отработал.
Логи: LLM_RESPONSE_INVALID, сохранён сырой ответ в raw_data_json (без секретов).

NEG-06: Stop во время обработки конкретного контракта

Ожидаемо: корректная остановка “после текущего шага”, не оставляем БД в полузаписанном состоянии.
Логи: stop_flag detected, транзакция закрыта.

4) Варианты тестирования “через браузер” глубже (без автотулов)
4.1. DevTools: Network

Что проверять:

Каждый API вызов имеет request_id в response headers (или в body).

SSE поток:

приходит event: progress

приходит event: result_added

приходит event: done

Нет “лишних” запросов на каждую строку (N+1 в UI).

Что сохранять при баге:

скрин UI + точное время

4.2. DevTools: Console

Проверяем:

Нет ошибок JS (red errors)

Ошибки API показываются пользователю корректно (toast/banner), а не падают в консоль

4.3. Проверка “обновления страницы”

Запустить поиск, обновить страницу (F5).
Ожидаемо:

UI подхватит RUNNING поиск по истории,

результаты загрузятся из API,

SSE переподключится.

5) Логи: как ловить ошибки и быстро находить причину
5.1. Структура лог-событий (минимум полей)

Каждая запись лога должна содержать:

ts, level

service: backend/worker

request_id (для API)

search_id

reestr_number (если относится к контракту)

step (например, ParsePaymentsAndObjects)

elapsed_ms

error_code (если ошибка)

msg

5.2. Основные “якоря” поиска в логах

Поиск по search_id — основной ключ.

Если UI показывает “ошибка запроса” — сначала берём request_id из Network и ищем его в backend логах.

Если ошибка в обработке контракта — ищем reestr_number в worker логах.

5.3. Каталог кодов ошибок (обязателен)

INPUT_VALIDATION_ERROR

ZAKUPKI_FETCH_TIMEOUT

ZAKUPKI_PARSE_ERROR

DOC_DOWNLOAD_ERROR

DOC_TEXT_EXTRACT_ERROR

LLM_TIMEOUT

LLM_RESPONSE_INVALID

DB_CONSTRAINT_VIOLATION

STOP_REQUESTED

Правило: любой ERROR должен иметь error_code, иначе ошибка считается “некачественной”.

6) Сквозная проверка данных (E2E + DB sanity)

Для каждого завершённого поиска проверяем:

search_request.status = DONE/STOPPED/ERROR корректен

processed_count = фактически сохранённым результатам

Нет дублей по (search_id, reestr_number)

Для top-3:

accepted_for_nmc = true

selected_contract_ids содержит ровно 3 (если найдено ≥3)

Если AI score есть — есть и строки сравнения (spec_comparison_row) или сохранённый JSON сравнения.

8) “Как специально ломать систему” (chaos-lite) без сложных инструментов

Выключить LLM ключ/поменять base_url → проверить, что поиск не падает целиком

Задушить сеть/таймауты к zakupki → проверить ретраи и ERROR

Убить worker контейнер во время RUNNING → поиск должен перейти в ERROR/STOPPED с понятной причиной, а не зависнуть в RUNNING навсегда (нужен watchdog/heartbeat)

Перезапустить backend во время RUNNING → UI должен восстановиться (история/результаты из БД)
