Аудит соответствия проекта ТЗ и план доработок
1. Соответствие текущей реализации требованиям ТЗ
Полнота воркфлоу. Согласно детальному ТЗ, MVP должен покрывать весь процесс: поиск контрактов по КТРУ и параметрам → парсинг карточек и спецификаций → AI-анализ соответствия → выбор топ-3 контрактов → расчёт НМЦК[1][2]. В текущем коде заложен скелет этого процесса, но реализовано не полностью. Модуль поиска уже умеет выполнять реальный запрос на ЕИС: через класс ZakupkiClient выполняется HTTP-запрос к странице результатов и парсится список контрактов с общим числом найденных (found_total)[3][4]. Таким образом, этап поиска частично закрыт – система действительно получает HTML результатов и извлекает реестровые номера, ссылки, даты и общие цены контрактов[5][6].
Однако последующие этапы пока реализованы частично в виде заглушек. Этап парсинга деталей контрактов (спецификации «Объекты закупки» и вложений) пока не завершён: в коде воркера вместо реального разбора карточки используется упрощённый шаблон – система формирует строку specs_raw с базовой информацией (номер, дата, цена) и текстом требований из поиска, без реального извлечения характеристик[7][8]. Комментарии явно отмечают, что здесь должны подключиться этапы FetchContractCard, ParseCommonInfo, ParsePaymentsAndObjects, FetchAttachments и т.д., но сейчас это пока не реализовано и временно пропущено[7].
AI-анализ в кодовой базе предусмотрен и частично интегрирован. При наличии API-ключа DeepSeek выполняются запросы к AI: нормализация требований ТЗ и характеристик контракта и их сравнение. Так, в воркере после получения данных контракта вызывается ai.normalize(specs_raw) и затем ai.compare() для сопоставления с нормализованным ТЗ[9][10]. Результат AI возвращается строго в JSON по заданной схеме (score, match_type, manufacturer_found, списки расхождений и пр.), который сохраняется в поле ai_analysis каждой записи контракта[11][12]. Таким образом, AI-скоринг частично работает: система вычисляет match_type (Идентичный/Однородный) и ai_score (0–100) либо по реальному ответу AI, либо подставляет значения по умолчанию (если AI недоступен, сейчас проставляется NO_MATCH и score=0)[13][14].
Выбор top-3 и НМЦК. Логика автоматического выбора трёх контрактов реализована на стороне бэкенда. Сервис SearchService.auto_select_top_3 выполняет приоритетную сортировку результатов: сначала IDENTICAL перед HOMOGENEOUS, затем по убыванию AI score, затем по дате[15][16]. Выбранным контрактам проставляется флаг accepted_for_nmc=True и вычисляется средняя цена (НМЦК) – функция calc_nmc_avg считает среднее арифметическое из цен выбранных контрактов[17][18]. Эта функция вызывается в конце pipeline, после обработки всех результатов: воркер отмечает поиск завершённым (DONE), сохраняет рассчитанные selected_contract_ids и nmc_value в базу[19]. На фронтенде также продублирована логика расчёта НМЦК на клиенте – функция calcNMC() пересчитывает среднее по отмеченным чекбоксами контрактам[20][21] и отображает его в UI. Таким образом, функционал НМЦК (средней цены) присутствует и на бэке, и на фронте; в MVP используется простое среднее, как указано в ТЗ[22].
Незавершённые части. Несмотря на описанные заготовки, значимые фрагменты логики пока не реализованы или требуют доработки. Во-первых, многие методы сервиса поиска – заглушки. Например, SearchService.create_search, stop_search, list_searches, get_search_results и пр. сейчас просто выбрасывают NotImplementedError()[23][24]. Это значит, что API эндпоинты работают только номинально: при вызове POST /api/search должен бы создаваться новый поиск и запускаться Celery-задача, но фактически метод create_search не содержит кода (на этапе Эпохи 1). Судя по тестам, эти методы пока имитируются через mock-объекты[25][26]. Во-вторых, отсутствует реализация остановки поиска: API-метод POST /search/{id}/stop определён и UI вызывает его при нажатии кнопки “Остановить”, но на бэкенде метод stop_search пока тоже не реализован[27]. В pipeline есть проверки флага остановки (stop_requested) перед каждым этапом[28][29], то есть механизм прерывания предусмотрен, но выставление этого флага через API пока не работает.
Кроме того, генерация отчёта ещё не сделана: эндпоинт GET /search/{id}/report объявлен, но SearchService.generate_report – заглушка[30]. На фронте нажатие “Выгрузить отчёт” пока просто показывает toast-уведомление “Отчет скачан” без реальной загрузки[31]. Не реализована и логика наполнения модального окна сравнения характеристик: UI модалка есть, а заполнение таблицы расхождений не выполнено – при клике “Сравнение” открывается пустая таблица[32][33]. Также, интеграция SSE-сообщений на бэкенде пока в тестовом режиме: воркер шлёт события в RedisStreams, а роутер отдаёт их через StreamingResponse[34][35], но метод stream_search_events в сервисе не реализован и, вероятно, используется напрямую брокер (Redis) в коде воркера. В целом, весь скелет функционала присутствует, соответствуя структуре ТЗ (поиски, результаты, SSE и т.д.[36]), однако значительная часть бизнес-логики – пустые заглушки или упрощения. Задачи итераций B/C/D из плана ТЗ (реальный парсинг контрактов, обработка 2025+ документов, полноценный AI-анализ) ещё не доведены до конца[37]. Проект находится на стадии “итерация A”, когда основные компоненты связаны между собой и UI подключен к API, но внутренняя обработка сделана минимально (с мок-данными и упрощениями)[38].
2. Соответствие фронтенда макетам (фронт13.html)
Фронтенд представлен одностраничным HTML (frontend/index.html), стилизованным с Tailwind и включающим JS-логику – фактически это доработанный макет фронт13.html под динамическое поведение. Структура HTML и визуальный стиль в целом соответствуют макету: присутствует шапка с заголовком “Поиск НМЦК” и иконкой поиска[39], боковая панель с формой новых поисков, вкладки “История поисков” и “Результаты поиска” в основной области, таблица результатов с фильтрами и модальное окно сравнения. Вёрстка повторяет макет вплоть до классов TailwindCSS, иконок FontAwesome и анимаций (например, класс .animate-fade-in для появления элементов)[40][41]. Таблица результатов имеет те же колонки, что и в макете: чекбокс для выбора, реестровый номер (№ контракта), год, цена за единицу, тип совпадения, производитель (с предупреждением для 2025+), AI score и кнопка “Сравнение”[42][43]. Эти элементы реализованы в шаблоне строки результирующей таблицы, создаваемом через innerHTML в функции renderResultsTable на фронте. Поля формы поиска тоже соответствуют ТЗ: наименование объекта, код КТРУ, производитель (опционально), регион (зашит СЗФО), период (3 года), лимит контрактов, а также многострочное поле характеристик товара[44][45]. В коде предусмотрена даже загрузка файла ТЗ: <input type="file" ... onchange="handleFile()"> с приемом .doc/.pdf/.html, после чего предлагается выбрать позицию лота из выпадающего списка[46][47]. При выборе лота (onchange="autoFillFromTz()") автозаполняются поля объекта и КТРУ демо-значениями (например, для “Бумага офисная A4” или “Моноблок офисный”)[48][49] – это реализует сценарий запуска поиска из файла, как в макете.
Поведение вкладок и окон. Переключение между “Историей” и “Результатами” работает через JS: функция switchTab(tab) активирует нужную вкладку и показывает соответствующий блок контента[50]. При переключении также управляется отображение нижней панели с НМЦК (скрывается на истории и появляется на результатах)[51]. Боковая панель на мобильных устройствах открывается/закрывается по кнопке “бургер” (ikona fa-bars) – в коде есть toggleSidebar() для добавления/удаления класса translate-x-full у бокового <aside>[52]. Модальное окно сравнения присутствует в DOM (с id="comparison-modal") и изначально скрыто (display: none). При вызове openComparison(id) модалке добавляется класс .open, что через CSS делает её видимой (backdrop + контент)[53][33]. Соответственно, кнопка закрытия вызывает closeModal(), убирая класс .open[54][55]. Всё это совпадает с логикой, заложенной в стилях макета (.modal-backdrop.open { display: flex; opacity: 1; } и т.д.[56]).
UX и удобство. Интерфейс оформлен аккуратно и почти полностью следует макету: используются те же отступы, цвета и стили (Tailwind конфигурирован так же, что видно по классам, напр. bg-gray-50, text-sm и пр.). Реализованы всплывающие уведомления (toasts) для обратной связи пользователю – например, при запуске поиска появляется showToast('Поиск запущен...', 'info')[57][58], при ошибках – красный toast. Имеется индикатор прогресса с полосой и счетчиком обработанных контрактов (0/30 и т.п.), появляется после нажатия "Начать поиск" вместо кнопки, что соответствует макету выполнения поиска. Боковая панель истории поддерживает пагинацию – показано по 10 записей, есть кнопки следующая/предыдущая страница, и фильтрация по полям (по названию, статусу, дате) – эти фильтры работают на фронте, фильтруя массив MOCK_HISTORY[59][60]. Однако, пока часть элементов функционирует на мок-данных или неактивна. “История поисков” сейчас не загружается с сервера, а генерируется на клиенте (массив MOCK_HISTORY с примерами и случайными записями)[60][61]. Фильтрация и пагинация истории выполняются в браузере, что противоречит ТЗ – по требованиям, таблицы должны поддерживать серверные фильтры/пагинацию[62]. Аналогично, данные результатов поиска initially берутся с бэкенда (через apiClient.listResults), но если запрос падает, код подставляет loadMockResults() – генерирует фейковые контракты случайно[63]. В текущем состоянии, учитывая что бэкенд не полностью функционирует, UI всегда работает на мок-данных, имитируя работу системы.
Несоответствия макету. Существенных визуальных отклонений от фронт13.html нет – разметка практически идентична (выложена из него же[64][65]). Однако найден баг в логике фильтрации фронта: в исходном макете в applyAllFilters() допущена синтаксическая ошибка – написано let filteredContracts = [.currentContracts] вместо [...][66]. Это приводило к неработоспособности фильтра по айди/score (ошибка в консоли). В предоставленном коде это уже исправлено на правильный синтаксис (filteredContracts = [...currentContracts] внутри фильтрации списка) или эквивалент[67]. Также не реализована подсветка выбранных контрактов в таблице по макету (в коде сделано: отмеченные чекбоксы строкам добавляют класс с голубым фоном и бордером[68], строки поднимаются наверх списка[69] – это соответствует ТЗ). Тем не менее, модальное окно “Сравнение характеристик” пока пустое – данные в таблицу сравнения (характеристика/требование/в контракте/статус) не выводятся, т.к. нет кода, который бы брал compare_res.rows из AI-анализа и наполнял #comp-table-body. На фронте отсутствует обработчик клика по кнопке “Сравнение” в каждой строке – он просто открывает модалку, но не заполняет <p id="comp-contract-id"> номером контракта и не генерирует строки <tr> внутри модалки. Это предстоит доделать, когда появятся реальные данные сопоставления. В целом, интерфейс удобный и соответствует макету по стилю и компоновке, но пока “живёт” в основном на статических данных. Как только API будет полноценно отдавать историю и результаты, фронтенд готов их принять – все нужные методы apiClient уже объявлены[70][71].
3. Соответствие полей БД требованиям ТЗ
В проекте описаны три основные сущности БД: search_request (поиск), contract_result (найденный контракт) и spec_comparison_row (строка сравнения характеристик). Их структуры полностью покрывают поля, указанные в ТЗ, без явных пропусков.
•	SearchRequest – модель поиска (таблица search_request). Поля соответствуют ТЗ[72][73]: UUID id, время создания (created_at) и обновления, status (статусы RUNNING/DONE/STOPPED/ERROR), источник запроса (input_source: MANUAL или FILE), object_name, код КТРУ (ktru_code), ОКПД2 (если есть), регион заказчика (customer_region, в MVP фиксирован СЗФО), закон (law, 44-ФЗ), даты периода date_from/date_to, статусы исполнения execution_statuses (у нас массив строк, напр. ["EC","ET"] для «исполнение завершено/прекращено»), лимит контрактов limit_contracts. В коде эти поля видны в модели: например, object_name, ktru_code и okpd2_code объявлены строковыми полями[74], регион, закон, даты – тоже присутствуют[75]. Поля прогресса и результата поиска тоже есть: found_total (число найденных) и processed_count (сколько обработано) со значениями по умолчанию 0[76], nmc_value – Decimal для рассчитанной НМЦК (nullable)[77], selected_contract_ids – массив UUID для хранения выбранных контрактов (топ-3)[77]. В ТЗ требовалось хранить выбранные ID и НМЦК[78][79] – это выполнено. Дополнительно, реализация БД содержит поля, не упомянутые напрямую в ТЗ, но полезные: например, runtime_ms (время выполнения поиска в миллисекундах), error_code и error_message для фиксации ошибок, флаг stop_requested (был ли запрос на остановку) и celery_task_id – эти поля помогают в управлении процессом и отладке. Их наличие не противоречит требованиям – скорее, расширяет возможности (учёт отмены, идентификатор фоновой задачи и т.п.). Таким образом, схема search_request соответствует ТЗ на 100% по обязательным полям[80], плюс содержит дополнительные технические поля, что допустимо.
•	ContractResult – модель контракта (таблица contract_result). Поля также покрывают все пункты из ТЗ[81][82]: UUID id и внешний ключ search_id на поисковый запрос[83], реестровый номер контракта reestr_number, URL карточки contract_url[83], дата подписания sign_date (может быть NULL), цена за единицу unit_price (Decimal, nullable) и валюта currency[84]. Присутствуют поля для результатов сравнения: match_type (строка, предполагается "IDENTICAL"/"HOMOGENEOUS"/"NO_MATCH")[85], ai_score (Integer 0–100)[85], найденный производитель manufacturer_found и флаг совпадения производителя manufacturer_match[86], флаг is_2025_plus (контракт 2025 года или позже)[87], а также accepted_for_nmc (boolean, выбран ли контракт для расчёта НМЦК)[87]. Все эти поля прямо перечислены в требованиях ТЗ (например, accepted_for_nmc, manufacturer_found/match, is_2025_plus – есть в структуре)[88]. Кроме того, модель хранит specs_raw (сырые текстовые спецификации, если есть) и JSON-поля raw_data_json и ai_analysis[89]. raw_data_json содержит все распарсенные данные по контракту (это соответствует требованию сохранять всё скачанное для отладки), ai_analysis – полный JSON-ответ ИИ (score, rows и прочее). ТЗ упоминало необходимость строгого JSON от AI и логирование его – хранение в базе удовлетворяет этому[90]. Также добавлены error_code и error_message на случай ошибок обработки конкретного контракта. В целом, модель contract_result полностью соответствует требованиям: ни один требуемый атрибут не упущен, имена полей понятны и совпадают по смыслу с ТЗ.
•	SpecComparisonRow – строка сравнения характеристик (таблица spec_comparison_row). ТЗ определяет для неё: ссылка на контракт (contract_result_id), название характеристики, требуемое значение, фактическое значение, статус совпадения (MATCH/DIFF/UNKNOWN) и вес (важность)[91]. В коде эти поля есть: name, target_value, actual_value, match_status, weight[92]. Дополнительно добавлено поле reason – пояснение или причина расхождения (текст), которого нет в списке ТЗ, но оно вытекает из AI-схемы: в JSON сравнения от AI предусмотрено поле "reason" для каждой характеристики[93], его сохранение полезно для отображения, и база его поддерживает. Таким образом, спецификация сравнения реализована полностью, с расширением под хранение объяснения.
Стоит отметить, что разработчики уже подготовили миграции Alembic под эти таблицы, и индексы/уникальные ограничения тоже продуманы (например, уникальность пары search_id+reestr_number в ContractResult[94]). Поля именованы в snake_case и соответствуют принятому стилю. В итоге, структура БД соответствует требованиям ТЗ на уровне ≥ 100% (все оговорённые поля есть, плюс дополнительные для надежности), что подтверждается и описанием в анализе: “таблицы search_request, contract_result, spec_comparison_row – поля совпадают с ТЗ (есть прогресс, selected_contract_ids, ai_analysis/raw_data_json и т.д.)”[80].
4. Соответствие API между фронтом и бэком
Реализованные методы API. Backend API спроектировано в соответствии с ТЗ[95] и включает необходимые эндпоинты под префиксом /api/search[96]. В коде присутствуют маршруты FastAPI для: создания поиска – POST /api/search/[97], остановки поиска – POST /api/search/{id}/stop[98], получения списка поисков – GET /api/search с фильтрами[99], получения деталей одного поиска – GET /api/search/{id}[100], получения результатов – GET /api/search/{id}/results[101], обновления выбранных контрактов – PATCH /api/search/{id}/selection[102], и получения событий (SSE) – GET /api/search/{id}/events[34], а также скачивания отчёта – GET /api/search/{id}/report[103]. Все эти методы задокументированы и возвращают данные через Pydantic-схемы (например, SearchBrief, SearchResultItem и т.д.), определённые в app/schemas/search.py. Таким образом, состав API полностью покрывает функционал из ТЗ – вплоть до SSE и выгрузки отчёта[104]. На фронтенде подготовлен клиент apiClient с методами, совпадающими по URL: .createSearch(payload) → POST /search, .stopSearch(id) → POST /search/{id}/stop, .listSearches() → GET /search, .listResults(id) → GET /search/{id}/results, .patchSelection(id, ids) → PATCH /search/{id}/selection[70][71]. Базовый путь API (API_BASE) настроен как "http://localhost:8000/api"[105], так что фронт запрашивает те же маршруты, что и объявлены на бэке.
Передаваемые и мок-данные. На текущем этапе не все методы реально возвращают данные из базы. Метод POST /api/search сейчас всегда возвращает сгенерированный id и прочие поля без реальной обработки – в коде воркера по завершении поиска запись обновляется статусом DONE и заполненными found_total, avg и пр., и потом фронтенд может их получить. Но сразу после создания поиска фронт получает объект SearchBrief с минимальными полями (на основе результата service.create_search). Поскольку create_search пока заглушка, видимо возвращается объект со статусом “pending” и теми же параметрами (в тестах это мокается)[106][107]. Далее, фронт открывает SSE-соединение на /search/{id}/events. Серверный код публикует события в Redis Stream, а при GET /events эти события стримятся клиенту[35]. Судя по pipeline, отправляются события: progress (с полем found_total и шагом)[108], result_added (с данными нового контракта)[109][110], а в конце done (со статусом DONE)[111]. Фронтенд подписан на них: при progress обновляет прогресс-бар и счетчики[112], при result_added – делает loadResultsFromAPI(searchId) и перерисовывает таблицу[113][114], при done – показывает уведомление, помечает поиск завершённым и закрывает SSE[115][116]. Это соответствует спецификации live-обновлений по SSE[117].
Однако, из-за неоконченной реализации, часть данных берётся из моков. Например, история поисков на фронте пока не подтягивается через GET /api/search, а отображается из MOCK_HISTORY (т.е. моковые данные вместо реального ответа). Метод apiClient.listSearches определён, но нигде не вызывается – при загрузке страницы история не запрашивается с сервера, а инициализируется локально[59][60]. То же касается фильтрации/пагинации истории: реализовано на клиенте, хотя API предусматривает ?ktru=&status=&.... Для результатов поиска фронт делает запрос GET /search/{id}/results и обрабатывает ответ. Если бэкенд вернёт список, он преобразуется в currentContracts[118][119]. В случае ошибки (например, метод не работает), стоит блок catch – тогда вызывается loadMockResults() для генерации фиктивных результатов[120]. Сейчас, пока метод get_search_results в сервисе не реализован, фронт, вероятно, всегда падает в мок-режим, генерируя случайные контракты (10 шт или равное found_total)[121][122]. Таким образом, обмен данными фронт–бэк частично осуществлён, но ряд ответов имитируются.
Полнота API-функционала. Интерфейс API по названию методов охватывает всё ТЗ, но практическая реализация пока не полностью функционирует. Например, метод выбора контрактов PATCH /search/{id}/selection определён и вызывается фронтом при изменении чекбоксов[123]. Он должен сохранять выбранные ID и пересчитывать НМЦК. На бэкенде этот эндпоинт есть[102] и в теории должен возвращать обновлённый список результатов. Но SearchService.update_selection ещё не написан и просто raise NotImplementedError[124]. Вероятно, планировалось: на PATCH сервер отметит принятые контракты, пересчитает НМЦК и вернёт обновлённые данные. Пока же фронт после PATCH сам обновляет UI (добавляет/удаляет ID в MOCK_HISTORY, пересчитывает avg и перерисовывает историю)[125][20], то есть работает автономно. Функционал SSE в целом выдержан: фронт открывает EventSource, бэк шлёт нужные события. Но обработка ошибок SSE упрощена – в коде при eventSource.onerror просто закрывается соединение и логируется ошибка[126][127], и фронт показывает toast “Ошибка подключения к серверу событий”[126].
Выгрузка отчёта пока не реализована (API возвращает заглушку). UI метод exportReport() просто уведомляет о скачивании[31], но не делает window.open или fetch. Бэк-метод generate_report должен формировать ZIP с .xlsx и .json[103], но код не написан.
В тестах API проверяется соответствие схем (Pydantic-моделей) и формат ошибок, что говорит о намерении держать контракт строго определённым[128]. Также есть тесты эндпоинтов с мокированием сервисов – они подтверждают, что роуты возвращают правильные статусы и поля[129][130]. Это означает, что контракты фронт–бэк (поля JSON) согласованы. Можно заключить, что покрытие функционала API приближено к требованиям, но полностью заработает только после реализации серверной логики. В частности, SSE и выбор top-3 заложены правильно, отчёт пока нет, история/фильтры – предстоит дописать (серверную часть). В итоге, расхождений в дизайне API нет, есть лишь пробелы в реализацией некоторых методов.
5. Обзор качества кода (стиль, архитектура, потенциальные проблемы)
Стиль кода и единообразие. Кодовая база в целом оформлена аккуратно. Бэкенд написан на Python с соблюдением PEP8: имена переменных и функций в snake_case, классы в CapWords, максимальная длина строки ограничена (в конфиге указан Ruff line-length=100[131]). Применяются аннотации типов (в моделях SQLAlchemy – Generic [uuid.UUID], типы полей, в функциях – возвращаемые типы coroutine и т.д.), что указывает на строгий режим mypy[131]. В docstring’ах и комментариях часто используется русский язык – это не критично, но лучше выбирать единый стиль документирования (можно оставить русский, раз вся команда им владеет). Фронтенд-код – чистый JS, без сборщиков, но структурированный внутри HTML. Используется современный JS-синтаксис (let/const, стрелочные функции отсутствуют, но есть async/await). В целом, имена на фронте тоже осмысленные (obj-name-input, loadResultsFromAPI и т.д.), стиль консистентен. Небольшой стильовой изъян – смешивание русского и английского в коде: напр. showToast('Ошибка создания поиска: ...') – сообщения на русском, а имена функций на англ. Впрочем, это приемлемо.
Архитектура и разделение слоёв. Бэкенд спроектирован модульно: есть пакет app/api для контроллеров (FastAPI роутеры), app/schemas для Pydantic-моделей (DTO), app/infra/db для моделей БД и репозиториев, app/services для бизнес-логики, app/workers для фоновых задач, app/core для настроек, ошибок и логирования. Такое разделение отвечает принципу “Thin controllers, fat services” – роутеры только валидируют и вызывают сервисы[132], а вся логика сосредоточена в сервисах и воркерах. Это прослеживается: например, api/search.py все операции делегирует SearchService через Depends[133][134]. Репозитории инкапсулируют работу с БД (SearchRepo, ResultRepo) – т.е. SQLAlchemy запросы вынесены туда. Архитектура выдержана на уровне задумки, хотя пока часть сервисов пустые. Но имеется хорошая основа: даже EventBroker выделен (Redis Streams), DeepSeekClient – отдельный класс, парсер EIS тоже вынесен (ZakupkiClient). Логирование реализовано через кастомный логгер (structlog, судя по log().bind(...) в воркере[135][136]) – это правильно для отслеживания процесса.
Дублирование и эффективность. В коде нет явного дублирования больших кусков – функции достаточно обобщённые. Есть некоторая избыточность на фронте: например, фильтрация историй и фильтрация результатов – это похожие механизмы, реализованные отдельно (historyFilters vs applyAllFilters). Но это оправдано разницей данных. Небольшая проблема – разрыв между мок-режимом и реальным: много условных операторов “если ошибка – подгрузить мок”[63], что в будущем нужно будет убрать или заменить на полноценную обработку ошибок API. С точки зрения производительности, потенциально узким местом будет парсинг HTML (BeautifulSoup) и скачивание файлов – но без этого не обойтись. Важно, что разработчики учли throttling: ZakupkiClient._sleep_human вставляет случайную задержку между запросами (требование robots.txt)[137], а в случае 403/503 – экспоненциальный backoff[138][139]. Это говорит о внимании к эффективности и устойчивости.
Обнаруженные ошибки. Кроме упомянутого багa с фильтрацией на фронте, других явных ошибок синтаксиса или логики не выявлено. Один нюанс в API: в коде объединения роутеров возможно лишний префикс (в router = APIRouter(prefix="/api/search") и потом include_router с prefix="/search"[96][140]) – это потенциально ведёт к двойному /search/api/search. Вероятно, это опечатка в Markdown-описании; в реальном коде нужно оставить один уровень префикса. В целом код выглядит качественно с точки зрения типичных ошибок – используются контекстные менеджеры для сессий БД[141], async/await повсеместно для IO, учтены возможные исключения (например, try/except вокруг каждой бизнес-операции с генерацией ApiException с кодами ошибок[142][143]).
Улучшения. Есть несколько направлений для рефакторинга и доработки: - Привести форматирование и конфигурацию линтера в проекте, чтобы фронтенд-код тоже проверялся (можно подключить Prettier/ESLint для JS). Сейчас фронт – один HTML, но если он будет расти, стоит отделить .js и .css. - Повысить единообразие ответов API: уже добавлен обработчик api_exception_handler для ApiException[144], но можно убедиться, что все ошибки идут через него. По ТЗ нужен единый JSON ошибки с полями error_code, message, details – это учтено в обработчиках[145][146], но надо проверить, чтобы нигде не просочилась сырая 500 ошибка. - Оптимизация кода фронта: уменьшить использование глобальных переменных (сейчас много let currentContracts = [] и т.п. в глобальной области). Возможно, стоит постепенно перейти на модульность или фреймворк, но в рамках MVP допустимо оставить как есть. - Удалить/mock-данные при интеграции: после реализации бекенда нужно убрать initMockHistory()[59] и loadMockResults()[63], чтобы не было рассинхрона между реальными данными и устаревшими моками. - В плане производительности, можно подумать о более легковесном парсере HTML (но BeautifulSoup+lxml в принципе ок для наших объёмов). Также, AI-вызовы желательно выполнять с таймаутом и ретраями (DeepSeekClient, вероятно, имеет внутри это). Если нет – добавить таймауты, чтобы зависание AI не стопорило весь воркер[147]. - Стоит обратить внимание на тестирование: пока есть юнит-тесты на схемы и один интеграционный на API через TestClient с моками[106][129]. Нужно добавить больше интеграционных тестов: например, прогон полного сценария поиска с поднятым воркером (Celery) и фейковыми данными, чтобы отладить гонки событий SSE, повторный запуск, остановку. Сейчас, без таких тестов, есть риск не заметить проблем “в полях”[90].
В целом, код соответствует современным стандартам, особенно учитывая раннюю стадию. Стиль выдержан, архитектура модульная. Улучшения коснутся большей частью заполнения пропусков функциональности и полировки (логирование, тесты, удаление временных заглушек).
6. Общая оценка качества Эпохи 1 и прогресса по ТЗ
Качество выполнения Эпохи 1. Первая фаза (назовём её итерация A, или “собираемый MVP”[148]) дала успешный каркас системы. Все основные компоненты связаны: есть база данных с нужными таблицами, REST API, фронтенд подключён к API, фоновые задачи и SSE-уведомления настроены. То есть достигнута цель – end-to-end сквозной сценарий от нажатия кнопки на UI до фонового задания и обратно – но пока с упрощённой логикой. Критически, проект ещё не “работающий” в смысле пользы конечному пользователю, но фундамент заложен правильно. Код написан понятным языком, с комментариями, разбит по файлам; то есть поддерживаемость на хорошем уровне.
Прогресс относительно полного функционала. Если оценивать процент выполнения требований ТЗ, можно условно разбить на: - Итерация A (Эпоха 1): каркас + UI (реализовано). - Итерация B: реальный поиск контрактов (в значительной степени сделано: поиск по КТРУ и фильтрам работает, found_total и список контрактов получаем[4]). Можно считать, этот пункт выполнен на ~80% (нет разве что фильтрации на стороне сервера и, возможно, тонкостей сортировки). - Итерация C: парсинг карточек, “Платежи и объекты закупки”, вложения – пока не выполнено (0%). Есть минимальная заглушка вместо этого, так что тут предстоит 100% работы. - Итерация D: AI-скоринг + выбор 3 + НМЦК + отчёт – выполнено частично. Скоринг интегрован (на уровне вызова AI и обработки JSON – можно дать ~50% готовности: базовый механизм есть, но нужна донастройка промптов, обработка ошибок AI и улучшение качества сравнения). Автовыбор топ-3 и расчёт НМЦК реализованы полностью (100%). Выгрузка отчёта – 0%. В целом по блоку D можно сказать процентов 50% (AI задействован, но без отчетности и без проверки качества выдачи). - Итерация E: устойчивость (логирование, ретраи, дедупликация) – частично: задержки и ретраи для EIS есть, логирование есть, но кэширования/дедупликации пока нет. Процент ~30%.
Совокупно, покрытие функционала MVP можно оценить на примерно 50%. Основные пользовательские сценарии запускаются и доходят до результата (пусть даже фиктивного) – это уже много. База и API в основном соответствуют спецификации (ещё ~20%). Не реализованные критические куски (парсинг деталей, отчёты) – оставшиеся ~30%. Проценты условны, но ясно, что сделано порядка половины необходимой работы для полноценного MVP.
Качество исполнения задач Эпохи 1 можно оценить как высокое: разработчики не ограничились “хэппи-пас” функциональностью, а заложили инфраструктурные вещи (очередь задач, SSE, обработку ошибок, конфиги AI и т.д.), что часто упускается на ранних этапах. Это усложняет начальную стадию, зато в дальнейшем позволит быстрее нарастить функционал. Код Эпохи 1 прошёл базовые тесты, но ещё не проверен интеграционно (нет end-to-end теста всего цикла). Тем не менее, фундамент достаточно прочный, и продолжение разработки (Эпохи 2–4) можно вести параллельно командами благодаря хорошей модульности[149].
Вывод: Эпоха 1 выполнена качественно, но охватывает лишь около половины необходимой функциональности MVP. Фокус был на связывании компонентов; следующими шагами будет наполнение их реальной логикой и отладка под боевые условия.
7. Техспецификация проекта: стандарты кода и процесса
Чтобы дальнейшая разработка велась согласованно, предлагается следующий набор стандартов и правил для проекта:
•	Стиль кода (Python): придерживаться PEP 8 во всём проекте. Использовать автоформатирование (например, black или ruff) с максимальной длиной строки 100 символов[131]. Именование: модули и файлы – в lowercase_snake_case, классы – в CamelCase, переменные и функции – snake_case. Докстринги писать в одном стиле (например, короткое описание в первой строке, подробности ниже, использовать английский или русский последовательно). Типизацию применять строго везде (mypy – в режиме strict)[131], особенно на границах функций (параметры/возврат). Исключения: можно не типизировать локальные переменные, если очевидно. Для форматирования import’ов – использовать isort (стандарт: сначала built-in, потом external, потом internal).
•	Стиль кода (JavaScript): если фронтенд останется на “vanilla JS”, ввести правила ESLint (Airbnb или Google config) и форматирование Prettier. Основные соглашения: 2 пробела отступ, точка с запятой на конце, одинарные кавычки для строк. Именование в JS: функции и переменные – camelCase (например, openComparison), константы – UPPER_SNAKE_CASE, классы (если появятся) – PascalCase. Все обработчики DOM должны быть либо явно названы (onClickFetchResults) либо инлайн как сейчас – допустимо, но лучше вынести в отдельный файл frontend/src/main.js для читаемости. Комментарии в коде – на том же языке, что и UI (здесь можно на русском, т.к. проект специфичный для русскоязычной сферы).
•	Стандарты наименований: Имена переменных и функций должны ясно отражать суть. Избегать аббревиатур, кроме общепринятых (req, resp, btn). Например, ktru_code ок, srch_res_lst – плохо, лучше results. Для бэкенда: Pydantic-схемы суффиксировать словами Request, Response, Item (уже так: SearchCreateRequest, SearchResultItem). Модели БД именовать в единственном числе (SearchRequest), таблицы – во множественном, если нужно (но тут совпадает). На фронте ID элементов DOM уже согласованы с их назначением (#obj-name-input, #results-body и т.д.) – следовать этому при добавлении новых.
•	Структура репозитория: Соблюдать текущую разбивку на директории. В корне репо должно быть две главные папки: backend и frontend. В backend/app структура уже задана модулями:
•	api/ – роутеры FastAPI (по ресурсам: search, возможно в будущем auth и т.д.).
•	core/ – настройки, утилиты (например, config, logger, constants).
•	infra/db/ – модели SQLAlchemy (models.py), миграции Alembic (в папке migrations/versions), сессия (session.py), репозитории (repos.py).
•	schemas/ – Pydantic-схемы запросов/ответов.
•	services/ – бизнес-логика, разбитая по доменам (сейчас search_service, возможно, в будущем file_service или ai_service).
•	services/zakupki/ – можно создать подмодуль для всего, что связано с парсингом сайтов ЕИС (ZakupkiClient, функции парсинга HTML и PDF).
•	workers/ – фоновые задачи Celery (tasks.py, celery_app.py). Здесь же можно держать утилиты для воркеров (например, _set_status, _check_stop – уже в tasks.py). Если будет расти, можно разбить по файлам (например, tasks/parse_contract.py и т.п.).
•	tests/ – модульные и интеграционные тесты (сейчас есть app/tests/test_api.py и пр.[150]; можно структурировать по подпапкам: unit/, integration/).
Папка frontend/ пока содержит статический index.html. Если фронтенд станет более сложным или будет использован фреймворк, можно организовать frontend/src/ (исходники) и сборку в frontend/dist/. Но для MVP это не обязательно – можно поддерживать один HTML + подключенные .js/.css файлы. Главное – версионировать их вместе с бэкендом.
•	Правила работы с Git (ветки, PR, Code Review): Принять модель GitFlow или trunk-based с фиче-ветками. Рекомендуется следующий подход:
•	Основная ветка main (или master) содержит всегда рабочую сборку MVP. Разработка новых фич идёт в отдельных ветках от develop (если введём промежуточную) или от main напрямую, но через PR.
•	Ветвление по эпикам/блокам задач: для каждой крупной задачи или эпика – своя ветка (например, feature/parse-contracts, feature/printform-ai и т.д.). Разработчики работают в своих ветках, регулярно мерджат из main чтобы синхронизироваться.
•	Pull Request’ы: Каждый PR должен сопровождаться описанием, какие изменения и зачем, ссылкой на задачу из трекера. Обязательна проверка одного-двух коллег перед слиянием (Code Review). Без апрува вливание в main/develop не допускается.
•	Мёрдж-конфликты: стараться минимизировать разбиением задач по разным областям кода (см. план параллельности ниже). Если конфликт возник – созваниваться командой, разбирать, чей кусок оставить или как объединить.
•	Коммиты: писать осмысленные сообщения на английском либо русском, но единообразно. Например: Add parsing of contract attachments, Исправлен баг фильтрации на фронте.
•	Теги и релизы: помечать релизные сборки тегами (v0.1, v1.0 etc.), чтобы можно было откатиться.
•	Логирование и обработка ошибок: Соблюдать правило – не подавлять исключения бесшумно. Везде, где есть try/except, логировать ошибку через структурированный логгер log() с достаточным контекстом. Например, в воркере уже делается logger.exception("pipeline_crashed", msg=str(e)) на непойманном исключении[151]. Аналогично, при любых сетевых вызовах (к EIS, к DeepSeek) – в случае ошибки выбрасывать AppError с кодом (например, ZAKUPKI_FETCH_ERROR) и человеко-читаемым сообщением, чтобы потом это попало в ApiException и ушло клиенту[152][153]. На уровне API – все ошибки должны преобразовываться в унифицированный ответ вида {"error_code": ..., "message": ..., "details": {...}}[154][146]. Для этого уже написаны хэндлеры api_exception_handler, http_exception_handler, validation_exception_handler[155][156] – их не удалять и не обходить. В фронтенде – при ошибках API выводить toast с сообщением (как сделано при ошибке создания поиска или обновления выбора контрактов[157][158]).
•	Уровни логов: INFO – для штатных операций (создан поиск, найдено N контрактов и т.п.), WARN – для ожидаемых проблем (поиск остановлен пользователем, не удалось найти элемент на странице, будет пропущен), ERROR – для исключений/сбоев. Логи Celery воркера и веб-сервера должны писаться в stdout (Docker best practice), а при деплое можно собирать их централизованно.
•	Безопасность в логах: не логировать содержимое документов ТЗ или контрактов (могут быть большие тексты) – достаточно логировать имя файла или ID контракта. API-ключи внешних сервисов в логах не показывать (настраивать логгер, чтобы, например, settings.deepseek_api_key не печатался).
•	Тестирование: Ввести правило: новый код сопровождается тестами. Минимально – unit-тесты на основные функции. Например, при реализации парсера контрактов – тестируем функцию на подготовленных HTML-примерах, при добавлении расчёта – тестируем функцию calc_nmc_avg (уже есть тест на среднее, кстати, проверяющий корректность вычисления)[159]. Стремиться к покрытию 80% и выше на unit-тестах. Также необходимы интеграционные тесты: поднятие тестовой БД (SQLite или Postgres в memory), запуск Celery таска с тестовыми данными и проверка, что по SSE приходят ожидаемые события, что статус поиска меняется на DONE, что selected_contract_ids сохраняются. Такие тесты можно запускать помеченными как slow (отдельным джобом CI). Отдельно – тесты API через TestClient (уже начато) – дописать кейсы: создание поиска с неверными данными (ожидать 422 с VALIDATION_ERROR), остановка поиска (имитация через mock сервиса), получение результатов (тоже через mock). В CI настроить запуск всех тестов на каждый PR.
•	CI/CD требования: Настроить непрерывную интеграцию, например, через GitHub Actions или GitLab CI. Pipeline должен включать этапы:
•	Lint/Format: запуск ruff и eslint для проверки стиля. Fail, если есть ошибки форматирования или типизации.
•	Tests: запуск всех тестов (backend и, при наличии, frontend) в headless-режиме. Использовать БД SQLite для скорости либо тестовый Postgres-сервис через docker-compose.
•	Build & Deploy (CD): при merge в main – собирать Docker-образы backend (и front, если нужно) и деплоить. Т.к. MVP предполагается без сложной инфраструктуры, можно настроить CD на сервер заказчика или в облако. Необходимо учесть миграции – при деплое выполнять alembic upgrade head. Сама сборка Docker уже есть (compose файл с Postgres, Redis, backend, worker)[160], проверить, что образы оптимизированы (например, использовать slim-образ Python, очищать pip cache).
•	Versioning: возможно, автоматически проставлять тег версии при мерже (semver, например).
•	Документация: Поддерживать актуальность README.md – описать там, как запустить систему (через Docker), как запускать тесты, где лежат конфиги. Документировать также .env.example (какие переменные нужны: DATABASE_URL, REDIS_URL, DEEPSEEK_API_KEY и др.). Для API целесообразно сгенерировать схему (например, подключить fastapi.openapi.json и на основе него сделать Swagger UI – FastAPI предоставляет/docs out of the box). Добавить раздел “Ограничения и допущения” – например, что без API-ключа AI система работает в ограниченном режиме (присваивает score=0 и NO_MATCH). Для разработчиков – завести файл CONTRIBUTING.md с основными правилами кодстайла и оформления PR (многое из перечисленного выше). Кроме того, техническую спецификацию (наш текущий документ) имеет смысл хранить и обновлять в репозитории, чтобы новые участники команды быстро освоили стандарты.
8. План доработки проекта (эпохи, эпики, задачи)
Разработка дальнейших итераций разобьём на эпохи (соответствуют крупным этапам из ТЗ[148][161]), внутри – на эпики (подзадачи), а те – на блоки конкретных задач. Задачи сгруппированы так, чтобы их можно было выполнять параллельно, минимизируя конфликты[149]. Ниже представлен план, особенно подробно расписан Эпоха 2 (следующий этап) с детализацией до задач уровня junior-разработчика.
Эпоха 2 — “Глубокий парсинг контрактов и извлечение цен”
Цель: Реализовать сбор необходимых данных по каждому найденному контракту. После этой эпохи система должна из каждого контракта получать спецификацию «Объекты закупки» (позиции, их характеристики, количество, цены) и вложения (Печатную форму) для контрактов 2025+, извлекать из них текст, определять цену за единицу и производителя. Это обеспечит полноту данных для AI-сравнения и расчёта НМЦК по правилам.
Epic 2.1: Парсинг HTML карточки контракта (спецификация)
Почему: Информация о позиции закупки (характеристики товара, количество, цена за единицу) зачастую содержится на вкладке “Платежи и объекты закупки” карточки контракта. Нам нужно автоматизировать извлечение этих данных, чтобы система могла сравнить их с требованиями ТЗ. Без этого AI-сравнение неполноценное, а цена за единицу может быть неизвестна.
Задачи:
1. Функция запроса HTML карточки. Добавить в ZakupkiClient метод fetch_contract_page(reestr_number) или fetch_contract_page_by_url(url). Он должен выполнять HTTP GET запрос по contract_url каждого контракта (например, URL типа .../contractCard/common-info.html?reestrNumber=..., который уже есть в FoundContractCard.contract_url[162][163]). Нужно соблюсти задержку (_sleep_human()) перед запросом и добавить отладочное сохранение HTML (по аналогии с fetch_results_html)[164][165]. Если запрос не успешен после нескольких ретраев – кидать AppError(ErrorCode.ZAKUPKI_FETCH_ERROR, ...).
Файлы: backend/app/services/zakupki_client.py (класс ZakupkiClient).
Ориентиры кода: смотреть на реализацию fetch_results_html[164][166] и build_results_url (как формируется URL)[167][168]. Для контрактов, у которых contract_url уже абсолютный, использовать напрямую, если относительный – дополнять базовым URL (см. код, где это делается при парсинге результатов)[169].
Критерии завершения: функция возвращает HTML строки карточки; при недоступности – поднимает понятное исключение. Покрытие тестом: смоделировать ответ (можно через VCR.py или сохранив реальный HTML в фикстуру) и убедиться, что функция возвращает строку нужной длины.
2. Парсер спецификации из HTML. Реализовать разбор HTML-кода карточки, чтобы извлечь таблицу спецификации. В BeautifulSoup найти раздел, который содержит позиции закупки. Обычно на странице есть вкладки, нам нужна "Объекты закупки" (можно искать заголовок или таблицу с колонками “Наименование, Количество, Цена за единицу” – структура известна из ЕИС). Возможно, придётся искать по классу или id. Написать метод parse_contract_spec(html: str) -> возвращает список позиций, где каждая – словарь: {"name": ..., "quantity": ..., "unit_price": ..., "manufacturer": ...}. Если какие-то поля не найдены, ставить None. Например, некоторые контракты могут не иметь производителя явно – тогда manufacturer = None.
Файлы: тот же zakupki_client.py или новый модуль zakupki_parser.py. Можно оформить как отдельную функцию или метод класса.
Подсказки junior: использовать BeautifulSoup(html, "lxml"), затем методы .find/.find_all. Например, сначала найти таблицу: soup.find("table", string=lambda txt: "Наименование" in txt). Либо найти все строки <tr> внутри нужного раздела. Элементы таблицы, скорее всего, будут в <td> последовательно: [наим, кол-во, единица изм., цена за единицу, сумма] – надо подтвердить по реальным примерам. Обратить внимание на разные представления чисел (могут быть пробелы, запятая в качестве разделителя десятичной части). Такие нюансы уже учитывались в парсинге цены в results (regex заменяет пробелы, запятую на точку)[170]. Использовать аналогичный подход.
Критерии завершения: На вход тестовой HTML (можно взять сохранённый контракт из ЕИС) функция возвращает корректный список позиций, содержащий хотя бы name, quantity (число или float), unit_price (Decimal) для каждой. Если таблица не найдена – бросает AppError(ErrorCode.ZAKUPKI_PARSE_ERROR). Тест: написать фиктивный HTML-фрагмент с одной строкой таблицы и проверить парсер.
3. Извлечение производителя из спецификации. Часто информация о производителе товара может быть присутствует в наименовании или отдельной графе. В закупках это не всегда есть, но предположим, что если в названии позиции фигурирует запятая и название фирмы, то это производитель. Задача: улучшить парсер из п.2, чтобы он пытался выделить производителя. Например, если name = "Тонер для принтера, Canon", можно парсить "Canon" как производитель. ТЗ требует помечать, если производитель не совпал с целевым[171][172]. Файлы: вместе с парсером спецификации.
Критерии: хотя бы в простых случаях функция выделяет производителя. Покрыть парой тестов (строка с производителем, строка без – возвращает None).

Однако, на MVP можно полагаться на AI. - Добавить логику принятия/отклонения контракта: на основе decision поля (AI может вернуть "ACCEPT" или "REJECT" в JSON). Если AI рекомендует не брать в расчёт (REJECT) – можно ставить initial accepted_for_nmc=False даже если он в топ-3 по score. Это правило из ТЗ не явно, но можно внедрить как улучшение. - Логирование: записывать весь compare_res в ai_analysis (уже делается) и добавлять в лог: logger.info("AI compare result", score=score, match_type=..., contract=reestr). Также, если есть причины (rows with reason) – писать их в debug.
Epic 3.4: Устойчивость AI-слоя
- Ограничить время вызова AI: добавить таймауты при запросах к DeepSeek (например, 60 сек, как указано в конфиге)[197]. Библиотека/клиент должны поддерживать timeout – настроить. - Добавить ретраи AI-запросов: если получаем от API 500 или таймаут – повторить 1-2 раза с backoff. Использовать настройки max_retries из конфига. - Логировать все запросы и ответы AI в файл (в JSON) для отладки. Например, сохранять промпт и ответ в zakupki_debug/ai_{search_id}_{contract_id}.json. Это поможет отслеживать, если AI дает неверные данные. - Добавить в error_code новых исключений: например, DEEPSEEK_TIMEOUT, DEEPSEEK_PARSE_ERROR – и при возникновении записывать их. Это уже учтено частично: ErrorCode.UNKNOWN_ERROR покроет, но лучше явно. - Метрики: опционально, добавить счётчик или лог времени AI-вызовов, чтобы оценить скорость (пока можно логом).
Эпоха 3 – больше про качество, поэтому задачи могут выполняться менее изолированно (они все про AI). Однако, можно параллельно: - Один разработчик настраивает DeepSeekClient и промпты (Epic 3.1, 3.2). - Другой – внедряет в pipeline использование этих новых методов (Epic 3.2, 3.3). - Третий – занимается обработкой ошибок и логированием (Epic 3.4). Они будут править иногда одни и те же файлы (например, search_service.py или tasks.py), но можно разделить: AI-вызовы вынести в отдельный модуль deepseek_service.py, над ним работать параллельно, а потом интегрировать в tasks.py единоразово.
Эпоха 4 — “Продакшн-харденинг: наблюдаемость, безопасность, CI/CD”
Цель: Подготовить систему к эксплуатации: обеспечить мониторинг, закончить документацию, настроить деплой, учесть безопасность и нагрузку.
Epic 4.1: Мониторинг и логирование в продакшне
- Настроить сбор логов: например, подключить Sentry для ошибок (в FastAPI middleware), Prometheus для метрик (Celery tasks duration, queue length). Добавить простой health-check эндпоинт. - Реализовать базовые метрики: количество поисков, среднее время поиска, % ошибок. Можно использовать prometheus-client и обновлять counters/gauges внутри кода (не критично, но хорошо иметь).
Epic 4.2: Безопасность и оптимизации
- Ограничить rate API: внедрить лимит (например, не более 5 поисков в минуту с одного IP) – в FastAPI можно через Depends + state. Особенно важно ограничить SSE/Events. - Защититься от слишком больших файлов ТЗ: если будут загружать DOCX на 1000 страниц – либо обрезать, либо предупреждать. В config можно поставить MAX_TZ_FILE_SIZE. - Дедупликация: к этому моменту накопится база скачанных печатных форм. Можно сделать кэш: если контракт с таким reestr_number уже парсили, не скачивать/парсить заново, а сразу взять из БД (если поиск повторяется). Хотя для MVP не обязательно, но снизит нагрузку. - Нагрузочное тестирование: с помощью JMeter или locust – прогнать, скажем, 50 поисков параллельно по 5 контрактов и посмотреть, держится ли система (Celery concurrency, использование Redis). По результатам – настроить, например, Celery concurrency=4, prefetch настроить, Redis maxmemory и пр.
Epic 4.3: CI/CD и выпуск релиза
- Дописать автоматизацию развёртывания: Docker Compose для продакшна (с volumes, рестартами). Сделать скрипт миграции. - Написать финальную документацию: user manual (как пользоваться UI, откуда берутся данные), технический паспорт (архитектура, технологии). - Провести code review всего проекта ещё раз и рефакторинг перед релизом: удалить отладочные распечатки, лишние мок-данные, привести структуру к финальному виду. Проверить соответствие ТЗ по чек-листу. - Финальный прогон интеграционных тестов и, при успехе, выкладка на сервер заказчика.
Эпоху 4 задачами дробить можно меньше, поскольку она больше про настройки. Здесь параллельно могут работать: - DevOps-инженер над CI/CD (если есть). - Разработчики над оптимизациями/метриками (каждый берет свой компонент). - Техписатель или тимлид над документацией.

Масштабирование команды и параллельная работа. Как отмечено, мы старались сгруппировать задачи так, чтобы разные люди работали над разными модулями без конфликтов[149]. Например, в Эпохе 2 блоки парсинга HTML и обработки PDF практически независимы и могут идти одновременно. В рамках одного эпика задачи выстроены от необходимых низкоуровневых к интеграционным: сначала пишем функции, потом встраиваем – это позволяет начать несколько задач сразу. Важно регулярно сливать изменения в общую ветку (или в develop) и писать тесты, чтобы интеграция проходила гладко. Благодаря модульности (разделение на zakupki_client, DeepSeekClient, services, frontend) команда из ~3–5 разработчиков сможет работать параллельно над разными частями системы, практически не наступая друг другу на ноги. Это обеспечит высокую скорость разработки и быстроту выхода на полнофункциональный MVP.
